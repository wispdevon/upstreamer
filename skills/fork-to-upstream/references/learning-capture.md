# Capture learning from a contribution

Identify a useful developer skill demonstrated by the actual work: tracing a prerequisite, designing a regression check, preserving attribution, or writing a maintainable handoff. Choose a concrete learning objective before a substantial exercise or adaptation.

Use the project's existing learning-note location and template. If no convention exists, include a concise note in the handoff rather than creating a new documentation system by default. Update an existing note when the same lesson gains evidence.

A useful note records:

- Title and project context, without secrets or private user data.
- Learning objective and developer usefulness.
- Problem, approach, reasoning, and the lesson observed.
- Evidence and limitations: exact commands, tested base/head or uncommitted state, outcomes, and what remains failed, blocked, or untested.
- Next practice: a small exercise with an observable outcome and verification method.
- Reusable skill or tool ideas, distinguishing implemented adaptations from proposed follow-ups with acceptance criteria and dependencies.

Keep learning proportionate to the contribution. Implement and verify a relevant exercise or reusable improvement within the current authorization. Put larger opportunities in the established backlog; do not let them expand the contribution implicitly.

The Upstreamer `/notes` journal captures these same concepts on the current browser/device. A user can download one note or the full journal as Markdown and provide it for adaptation into project notes. Browser entries do not synchronize with repository files, and this skill does not require access to the browser. Do not claim that entered evidence, saved notes, or completed exercises certify contribution readiness.

Respect the skill's publication boundary: notes and learning opportunities do not authorize pushes, PRs/MRs, maintainer messages, merging, or deployment.
